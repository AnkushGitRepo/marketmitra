# 0061 — The changelog follows Keep a Changelog 1.1.0

Status: accepted (2026-11-12, issue #182). Amends the changelog parts of [0051](./0051-version-management.md).

## Context

`CHANGELOG.md` is generated by `npm run release` from Conventional Commit subjects, grouped under "Features", "Fixes" and "Refactors". That is the "commit log diff" the [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) guide calls a bad idea: it is full of noise, it cannot say what matters to a reader (what will break, what was deprecated, what was a security fix), and the commit subject is written for developers, not users. There is no `[Unreleased]` section and no compare links.

## Decision

`CHANGELOG.md` follows Keep a Changelog 1.1.0 and [Semantic Versioning](https://semver.org/spec/v2.0.0.html), and says so in its header. The guide's principles, applied here:

1. **For humans, not machines.** One sentence per notable change, describing the effect for the reader ("Analysts that hit a temporary error are retried instead of stalling for good."), not a commit subject, a PR title or a file name. Several commits that make one change are one entry. A PR number in brackets at the end is welcome: `(#153)`.
2. **An entry for every version.** Every tag has a section. A version that was pulled because of a serious bug or a security problem stays in the file and is marked `## [X.Y.Z] - YYYY-MM-DD [YANKED]`.
3. **Grouped by type**, using only these six headings, in this order, and omitting any that would be empty:
   `### Added` (new features), `### Changed` (changes in existing behaviour), `### Deprecated` (soon to be removed), `### Removed` (now removed), `### Fixed` (bug fixes), `### Security` (vulnerabilities and hardening that closes one).
4. **Linkable.** Version headings are `## [X.Y.Z] - YYYY-MM-DD` and each has a reference link at the bottom of the file: `[X.Y.Z]: https://github.com/AnkushGitRepo/marketmitra/compare/vPREV...vX.Y.Z`, and `[Unreleased]: .../compare/vLATEST...HEAD`.
5. **Newest first**, each with its **release date in ISO 8601** (`YYYY-MM-DD`, the day the release is made).
6. **An `## [Unreleased]` section at the top**, always present. Every PR that makes a notable change adds its entry there in the same PR; at release time its contents move into the new version section and a fresh empty `[Unreleased]` is left behind. A deploy is not a release (ADR 0059), so `[Unreleased]` simply keeps accumulating across deploys.
7. **Always list breaking changes, deprecations, removals and security fixes**, even small ones. Prefix a breaking change with **Breaking:**. (Before 1.0.0 a breaking change is a minor bump, per ADR 0051.)
8. **Be consistent about what is notable**, because a changelog that mentions only some changes is dangerous: readers will treat it as the single source of truth.

### What is notable, and what is not

| Notable (write an entry) | Not notable (leave out) |
|---|---|
| A feature or page a user can see or use; a new or changed API route (anything in `public/openapi.json`) or MCP tool | Refactors with no visible effect, renames, formatting |
| A behaviour change, a changed default, a new limit | Tests, docs-only changes, CI and tooling, the handoff and session log |
| A new or changed environment variable or setting an operator must act on; a database migration | Dependency bumps (unless they fix a vulnerability, which is a **Security** entry, or change behaviour) |
| A bug fix a user could have noticed | A fix to something that never shipped |
| Anything deprecated or removed; anything breaking | |
| A vulnerability fixed or an exposure closed, even one found by us | |

### Conventional Commit types as a starting point

The commit type helps draft an entry but does not decide it. `feat` is usually **Added** (or **Changed** when it alters something that exists); `fix` is **Fixed**, or **Security** when it closes a vulnerability whatever its type; `perf` and `refactor` are **Changed** only if the reader can notice; `!` or a `BREAKING CHANGE:` footer is **Changed** or **Removed** with **Breaking:**; `docs`, `test`, `chore`, `ci` and `style` are left out unless they matter to a user.

### Example (illustrative)

```markdown
## [Unreleased]

### Security

- The data service no longer shows SQL or driver details in error responses, and no longer creates a company for a symbol that is not an NSE listing. (#176)

## [0.5.0] - 2026-11-11

### Added

- The stock page has one research container with tabs (All points, Supports, Weak spots, Valuation) and a computed valuation sensitivity check that needs no AI key. (#153)
- Retry all stalled on the analyst desk, and one primary action per analyst card. (#151)

### Fixed

- Analysts that hit a temporary error are retried instead of stalling for good. (#150)
```

## Transition

The release script (`scripts/release.mjs`, `src/lib/release/release.ts`) still writes "Features / Fixes / Refactors" sections from commit subjects and inserts a new section above the first `## [` heading, so adding an `[Unreleased]` heading to the file now would make releases land above it. Until issue #183 aligns the script and converts the existing 0.2.0 to 0.5.0 sections:

- write every new entry in this format and keep the notes in the PR description;
- the **release PR hand-edits the generated section** into this format (six headings, curated sentences, no commit subjects, nothing noisy) before it is merged, and adds the compare links;
- do not add `## [Unreleased]` to `CHANGELOG.md` yet.

The GitHub Release for a version uses that version's changelog section (the Release workflow already does this), so curated entries also make better release notes. Rewriting an existing changelog to fix it, for example to add a forgotten breaking change, is fine.

## Consequences

- Readers can see what a release means for them, including what will break.
- Every notable PR carries a one-line changelog entry (a PR template checkbox asks for it); the release step becomes a review of curated text instead of a dump of commit subjects.
- Small fixes still do not need a version of their own (ADR 0059): they sit in `[Unreleased]` until a release is asked for.
